# 개발 하네스

이 저장소는 앱만이 아니라 앱을 만드는 방법도 함께 담습니다. 사람 한 명이 여러 코딩 에이전트를 팀으로
돌리고, 실수는 사람의 기억 대신 기계 검사로 막습니다. 저장소를 받으면 같은 방식으로 일할 수 있어야 하고,
개인 설정(`~/.claude` 같은)에만 있는 규칙은 없어야 합니다.

English: [HARNESS.en.md](HARNESS.en.md)

## 한눈에

```
사람(결정)
  └─ 팀장 에이전트: 일을 쪼개고, 맡기고, 검수하고, 합친다
       ├─ 작업자: 개발      ┐
       ├─ 작업자: 조사      ├─ 각자 자기 git worktree 와 브랜치에서 커밋까지만
       └─ 작업자: 적대 리뷰 ┘
                    │
   기계 검사: git 훅 → Claude 훅 → CI → 테스트 배포
```

네 층으로 나뉩니다.

| 층 | 어디에 | 하는 일 |
|---|---|---|
| 규칙 | `AGENTS.md`, `CLAUDE.md` | 모든 에이전트가 먼저 읽습니다. Claude, Codex, Antigravity, opencode 가 같은 파일을 봅니다 |
| 기계 검사 | `.githooks/`, `.claude/hooks/`, `.codex/hooks.json`, `.github/workflows/` | 규칙을 어기면 커밋, push, 명령 실행 단계에서 거절합니다 |
| 스킬 | `.claude/skills/` | 자주 하는 일의 순서와 기준 문서를 묶어 둡니다 |
| 팀 도구 | `tool/team/` | tmux 팬 사이로 일을 보내고(`itl`), 팀을 한 번에 띄웁니다(`start.sh`) |

## 준비

필요한 것은 도커, git, python3, tmux, GitHub CLI(`gh`), 그리고 쓰려는 에이전트(Claude Code 등)입니다.
Flutter 는 도커 이미지 안에 있으니 깔지 않습니다.

```bash
git clone <저장소> && cd <저장소>
tool/setup.sh              # git 훅을 켜고 패키지를 받습니다
tool/test.sh               # 전부 통과해야 시작한 것입니다
tool/team/start.sh         # 팀장 1, 작업자 N 팬을 띄웁니다. 사용법은 tool/team/README.md
```

자세한 설치와 첫 빌드 시간은 [DEV-ENV.md](DEV-ENV.md) 에 있습니다. 이 준비를 에이전트에게 맡기려면 [AI_SETUP.md](AI_SETUP.md) 를 주면 됩니다.

## 역할

| 역할 | 하는 일 | 하지 않는 일 |
|---|---|---|
| 사람 | 무엇을 만들지, 무엇이 맞는지 정합니다. 실기기에서 손맛을 판정합니다 | 코드 세부를 직접 지시하지 않아도 됩니다 |
| 팀장 | 일을 T번호로 쪼개 맡기고, 보고를 검수해 통합 브랜치에 합치고, 테스트 뒤 push 합니다. `docs/TEAM.md` 를 혼자 고칩니다 | 작업자 브랜치에서 직접 고치지 않습니다 |
| 작업자(개발) | 자기 worktree 에서 맡은 범위만 고치고 커밋합니다 | push, PR, 합치기를 하지 않습니다 |
| 작업자(조사) | 출처와 확인 날짜가 달린 근거를 문서로 남깁니다 | 근거 없는 추천을 하지 않습니다 |
| 작업자(적대 리뷰) | 남이 만든 것을 깨 보고 문제만 심각도 순으로 보고합니다 | 코드를 고치지 않습니다 |

에이전트 제품을 섞어 씁니다. 같은 모델은 같은 곳을 놓치기 때문에, 리뷰는 만든 쪽과 다른 회사 모델에 맡깁니다.

## 일 하나가 도는 순서

1. **맡기기.** 팀장이 `tool/team/itl send <이름> '…'` 로 보냅니다. 한 번에 아래를 다 적습니다.
   - T번호, 브랜치 이름, 기준 커밋
   - 범위: 고칠 경로, 고치지 말 경로
   - 완료 기준: 어떤 검사가 통과해야 하는지, 무엇을 실제로 돌려 봐야 하는지
   - 아직 사람이 정하지 않은 것은 상수 하나로 감추라는 지시
2. **작업.** 작업자는 자기 worktree 에서만 일합니다.
   `git worktree add ../<저장소>-<이름> -b <브랜치> <기준 커밋>`
3. **보고.** 커밋까지 하고 `itl send <팀장 팬> '…'` 로 보냅니다. 브랜치와 커밋, 세 줄 요약, 명세와 다르게
   판단한 점, 실제로 돌려 본 결과(통과 개수, 걸린 시간), 남은 문제를 적습니다. 실패와 건너뛴 것도 그대로 씁니다.
4. **검수와 합치기.** 팀장이 변경을 읽고 통합 브랜치에 `--no-ff` 로 합친 뒤 `tool/test.sh && git push` 를 한
   명령으로 돌립니다. 충돌은 합치는 쪽이 아니라 그 코드를 만든 작업자에게 돌려보냅니다.
5. **CI 와 배포.** CI 가 안드로이드, iOS, macOS 빌드까지 돌립니다. iOS 테스트 빌드는 서명 없는 `.ipa`
   아티팩트로 나옵니다. 둘 다 같은 커밋에서 만든 파일만 테스트 배포에 올립니다.
6. **`main` 으로.** 통합 브랜치가 쌓이면 PR 하나로 `main` 에 합칩니다. `main` 에는 PR 로만 들어갑니다.

팬은 이름으로 부릅니다. `start.sh` 가 팀장 팬을 `leader`, 작업자 팬을 준 이름(`ui`, `api` 같은)으로 붙이고,
`itl send` 는 보내는 쪽 이름을 `[from ui · reply: itl send ui '…']` 처럼 앞에 붙여 받는 쪽이 바로 답할 수 있게 합니다.
이 저장소를 처음 만들 때는 tmux 탭 번호(`12.1` 팀장, `12.2`~`12.6` 작업자)로 불렀습니다. 기록에 나오는 번호는 그 이름입니다.

맡기는 말과 보고는 실제로 쓴 그대로 [prompts/](prompts/README.md) 에 역할별로 남겨 두었습니다. 작업 목록은 [TEAM.md](TEAM.md) 에 있습니다.

## 기계가 지키는 규칙

사람이 기억해야 하는 규칙은 결국 어겨집니다. 한 번 어긴 규칙은 검사로 바꿉니다.

| 규칙 | 막는 곳 | 생긴 이유 |
|---|---|---|
| 개인정보와 서버 정보를 넣지 않는다 | `privacy_scan.py`: pre-commit, commit-msg, pre-push, CI | 공개 저장소입니다. 실제 IP, 도메인, 이메일, 홈 경로, 키는 한 번 올라가면 지워도 남습니다 |
| AI 티와 장식을 넣지 않는다 | `slop_scan.py`: 같은 자리 | 엠대시, 꾸밈 이모지, 코드 안 한글, 그라데이션과 그림자를 기계로 거릅니다 |
| 테스트 없이 push 하지 않는다 | `.githooks/pre-push`, Claude 훅 | 테스트가 훅 환경 변수를 물려받아 통합 브랜치에 가짜 커밋을 만든 적이 있습니다. 지금은 `test_git_isolation.py` 가 막습니다 |
| `main` 에 바로 push 하지 않는다, 훅을 건너뛰지 않는다 | pre-push, Claude 훅 | `--no-verify` 한 번이면 위 검사가 전부 꺼집니다 |
| 공유 stash 를 맨손으로 쓰지 않는다 | Claude 훅 | worktree 끼리 stash 를 같이 씁니다. 남의 변경을 꺼내 버립니다 |
| 기다리며 확인을 반복하지 않는다 | Claude 훅 | 에이전트의 도구 호출은 명령이 아무리 가벼워도 대화 전체를 다시 읽습니다. 백그라운드로 띄우고 끝나면 알림을 받습니다 |
| 세 언어가 같은 키를 가진다 | `l10n_check.py` | 한 언어만 고치고 넘어가는 일이 잦습니다 |
| 테스트와 분석은 메모리 4GB 안에서 돈다 | `tool/fl` (도커 `--memory 4g`, 추가 스왑 없음) | 여러 작업자가 한 서버에서 테스트를 같이 돌립니다. 테스트 하나가 메모리를 다 먹으면 서버 전체가 멈춥니다. 2026-11-19 실측 최고 2.4GB 입니다. `FL_TEST_MEMORY` 로 바꿉니다 |
| 디자인 값은 토큰에서만 | `gen_tokens.py --check` | 화면 코드에 색과 간격을 직접 쓰면 디자이너가 고칠 곳이 흩어집니다 |
| 응원 문구가 근거 규칙을 지킨다 | `cheers_check.py` | 화남, 슬픔, 불안에 느낌표, 이모지, 웃음, 금지어를 막습니다 |
| CI 가 빨간불이면 넘어가지 않는다 | GitHub PR 검사 | iOS 빌드가 하루 동안 조용히 실패했습니다. 리눅스에서는 iOS 코드를 컴파일할 수 없어서 아무도 몰랐습니다 |

각 훅과 검사기에는 테스트가 있습니다(`tool/test_*.py`, `tool/test_fl_wrapper.sh`). 오탐은 검사기의
진짜 위험이라, 막지 말아야 할 예도 테스트에 넣습니다. 정말 괜찮은 줄만 `privacy-ok`, `slop-ok` 를 적습니다.

## 사람이 지키는 습관

기계로 가리기 어려운 것들입니다. 리뷰에서 봅니다.

- **실제 결과로 말합니다.** "됐을 것입니다" 대신 돌려 본 명령과 결과를 적습니다. 실패한 단계, 건너뛴
  단계도 보고합니다. 진동과 애니메이션의 손맛은 실기기에서만 판정합니다.
- **근거가 먼저입니다.** 이 앱은 우울한 사람을 위한 앱이라 문구 하나도 논문 근거를 따릅니다.
  조사 보고서([EVIDENCE.md](EVIDENCE.md)) → 여섯 가지 핵심 가치([PRINCIPLES.md](PRINCIPLES.md)) →
  검사 규칙(`tool/cheers_rules.json`) → 검사기 → 스킬 순서로 내려옵니다. 근거가 바뀌면 위에서부터 고칩니다.
- **탐색은 묶어서 한 번에 합니다.** 파일 조각을 하나씩 들여다보는 호출을 이어 붙이지 않습니다.
  필요한 파일과 범위를 먼저 정하고 한 번에 뽑습니다.
- **되돌릴 수 있는 일은 묻지 않고 진행합니다.** 사람이 정할 것(이름, 정책, 비교 표시처럼 원칙과 부딪히는
  것)은 상수 하나로 감춰 두고 일을 계속합니다. 되돌리기 어려운 일(공개, 삭제, 배포)은 먼저 묻습니다.
- **막히면 오래 붙들지 않습니다.** 30분이 넘으면 막힌 이유를 보고합니다.
- **사본을 남기지 않습니다.** `.bak`, `.old` 를 만들지 않습니다. 되돌릴 근거는 git 에 있습니다.

## 스킬

`.claude/skills/` 에 있습니다. 에이전트가 해당 일을 할 때 스스로 불러 씁니다.

| 스킬 | 언제 |
|---|---|
| `cheers-write` | 응원 문구를 쓰거나 고칠 때 |
| `principles-check` | 새 기능, 화면, 문구를 핵심 가치와 안전 기준에 대어 볼 때 |
| `l10n-add` | 화면 문구 키를 추가할 때 |

스킬은 짧게 쓰고 저장소의 기준 문서를 가리킵니다. 기준이 두 곳에 적히면 한쪽이 낡습니다.

## 다른 프로젝트로 옮기기

앱 코드와 상관없는 부분은 그대로 가져갈 수 있습니다.

1. `AGENTS.md` 의 git, 개인정보, 글쓰기 절과 `CLAUDE.md` 를 가져와 프로젝트 설명만 바꿉니다.
2. `tool/privacy_scan.py`, `tool/slop_scan.py` 와 테스트, `.githooks/`, `tool/setup.sh` 를 가져옵니다.
   한글 금지나 평면 스타일 같은 프로젝트 규칙은 `slop_scan.py` 에서 끄거나 바꿉니다.
3. `.claude/` 의 훅과 설정, `tool/team/` 을 가져옵니다.
4. `docs/HARNESS.md` 와 `docs/TEAM.md` 를 새 프로젝트에 맞게 고칩니다.
5. 첫 사고가 나면 그 자리에서 검사기 하나와 테스트 하나를 더합니다. 하네스는 그렇게 자랍니다.
